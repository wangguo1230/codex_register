# :3100 反复卡死（40GB+）事故报告

- 日期：2026-08-19
- 实例：`wuyan-2.local`（本机 `192.168.1.100`，库 `192.168.1.126:5432/all_register`）
- 进程：`npx tsx server/index.ts` 监听 `0.0.0.0:3100`
- 结论先说：**不是“2 个并发就会占几十 GB”。是 HTTP 主进程里做了本机 SOCKS 转发环，把 kookeey / 浏览器流量泵进 V8，事件循环堵死，GC 收不回，进程内看门狗也跑不动。**

---

## 1. 现场

反复出现同一形态：

| 项 | 卡死时 | 本次拉起后（约 3 分钟） |
|---|---|---|
| PID | `56064`（此前还有多次同类进程） | `57439` |
| RSS | **约 44.6 GB**（`ps` 看到 `46795632` KB） | **约 244 MB** |
| CPU | 85%–94% | ~0% |
| HTTP `/api/health` | 超时（页面全卡） | `ok=true, rssMb=244` |
| 监听 | `*:3100` + **`127.0.0.1:53210` SOCKS** | 只有 `*:3100` |
| 本机套接字 | `53210 ↔ 53211` 自环 ESTABLISHED | 无转发环 |
| 启动参数 | `MAILCOM_HEADLESS=1 MAIL_JOBS_PAUSED=1` | 同上，并加了 `SKIP_STARTUP_RECOVERY=1` |
| 整备 | 已暂停领取，仍卡死 | 仍暂停 |

关键证据：卡死进程里有一条 **本机无账密 SOCKS 监听 + 自己连自己** 的转发环。这就是 `openNoAuthSocksToAuthedProxy()` 在 `:3100` 里跑起来的特征。

即使 `MAIL_JOBS_PAUSED=1`（不领邮箱整备），测 AT / 刷 RT / 导出 / 换绑对账仍会走这条路径，所以“整备停了还会卡”。

## 2. 根因（按杀伤力）

### 2.1 主因：主进程里的 kookeey 本地 SOCKS 转发环

`probeAtViaPool` / `refreshRtViaPool` 曾为了“走 GPT 代理池过 CF”，对带账密的 socks5 出口调用：

```
openNoAuthSocksToAuthedProxy(kookeey, jump)
  → 在 127.0.0.1:随机端口 listen 一个无账密 socks
  → 客户端（undici fetch）连这个口
  → client.pipe(upstream); upstream.pipe(client)
```

Playwright / 比特浏览器不能带 socks5 账密，这个转发器本来是给**浏览器子进程**用的。把它放进 HTTP 神进程后：

1. Node 把上下游都读进同一条事件循环；
2. `fetch` abort / 对端慢 / TLS 半开时，`pipe` 缓冲不会随着 JS 对象一起消失；
3. 一条环就能把 RSS 从几百 MB 打到几十 GB；
4. CPU 被 `uv__stream_io` 占满，HTTP/SSE 全部超时。

本次卡死现场只有这一条环，没有整备 Chrome，对应就是 AT/RT 探测。

### 2.2 次因：Node 24 实验性 `ProxyAgent(socks5://…)`

`undici` 的 SOCKS 实现会把流读进主进程。本机 `10808` 是 **v2rayN 的 HTTP 代理**，曾经被当成 `socks5://127.0.0.1:10808` 喂进去，同样能灌内存。

已改为：`10808` 一律走 `http://127.0.0.1:10808`；其它 socks 走 `createProtocolDispatcher`，不再用实验 SOCKS Agent。

### 2.3 次因：Playwright / 比特 CDP 挂在 :3100

mail.com 验密、Gmail 整备、换绑开窗若在主进程连 Chrome/比特，CDP 协议流同样进 V8。  
表现：consent 墙误判、50s 超时后 Chrome 变孤儿、并发 2 也能到 30GB+。

已做一部分隔离（mail.com 验密派子进程），Gmail/比特 **还没完全拆出去**。

### 2.4 次因：子进程 stdout 无上限 `buf += chunk`

worker 若吐超大无换行 JSON/HTML，主进程字符串会线性膨胀。  
已对调度 / 换绑探测 / 发信 / mail.com 验密加了约 512KB 环形缓冲。

### 2.5 为什么“限制并发”挡不住、GC 也不回收

- 限制的是**任务个数**，不是**每个任务能抓住多少可达内存**。
- 转发环、CDP、未关的 Chrome、未 abort 的 socket 都还被引用，GC 不会收。
- `Promise.race(50s)` 超时只让业务失败，**不杀浏览器、不拆 pipe**，泄漏继续。
- 2 个并发 × 无界缓冲 ≠ 2×20MB，可以是 2 条一直灌的流。

### 2.6 为什么进程内 RSS 看门狗没把 44GB 杀掉

`rss-guard` 用 `setInterval` 看 RSS≥3200MB 再 `parkWorkForRestart`。  
事件循环已经被 stream 占满时，定时器**不会跑**；即便跑到了，`parkWorkForRestart` 还要写库，库连接也堵，重启发不出去。

所以必须有一个**进程外**看门狗，用 `ps` 看 RSS，超标直接 `SIGKILL`。

## 3. 周边问题（同一周里一起出现，容易误判）

这些不是 44GB 的直接原因，但会让人以为“代理坏了 / 导出坏了 / 2FA 错了”：

| 现象 | 实际 |
|---|---|
| 验密失败写「验密超时(50s)」 | 主进程 `Promise.race` 先超时，密码未必错；Chrome 还留着 |
| consent 墙极慢 | 首页 cookie 文案被当成墙；`/Continue/i` 过宽；iframe `isVisible(350ms)` 打满 |
| 导出 sub2json 409「已有导出在跑」 | `exportRtBusy` 被卡住的 coy 占着；已有 RT 的号也被锁 |
| RT 并发一直是 2 | 代码写死 `min(2)`，没读 `scheduler.rtConcurrency`（配置是 4） |
| 换出口仍 429 | `AuthorizeContinue` 限流；429 应停，不应换 IP 重打 |
| coy SSL 失败、ena 成功 | 同一 10811 跳板，不同 kookeey session；不是“代理整体不行” |
| 10811 当出口 | 10811 是 xray **跳板入口**，不是住宅出口 |
| IMAP「重试」没日志 | 卡在 `tryImapOtpOnce` 拉全文 MIME，心跳没打出来 |
| lukavasileski123 的 2FA「不对」 | Gmail 密钥 `YLRJQPZI…` 现场登录是对的；ChatGPT MFA 是另一把 |
| 重启后立刻再 OOM | 启动恢复把整备 / 换绑一次性重新入队，比特+SOCKS 再进 3100 |

业务约定（保持）：

- **429 = 停**，不要换出口重试。
- **10808** = 本机 v2rayN，ChatGPT HTTP 用 HTTP 代理，不要当 socks5。
- **10811** = 跳板，不是出口。
- GPT 跳板为空时，直连代理池，不要借用邮箱跳板。

## 4. 已落地的修复

### 4.1 主进程禁止本机 SOCKS 转发（针对本次 44GB）

- `server/index.ts`：`CODEX_HTTP=1`
- AT / RT 不再租 kookeey、不再 `openNoAuthSocksToAuthedProxy`
- 短 HTTP 走本机 `http://127.0.0.1:10808`
- IMAP 预检把带账密的出口 URL 直接给 ImapFlow，不在 3100 包一层跳板转发
- `src/mail/proxy-chain.ts`：主进程调用 `openNoAuthSocksToAuthedProxy` / `wrapExitThroughJump` 直接抛错
- Gmail 比特 / 代理探测若还在 3100 里，捕获该错误后改为直连出口，不再硬套转发环

### 4.2 看门狗

- 进程内：RSS 900 警告 / 1800 拒开浏览器 / 3200 先退回队列再重启；退回最多等 2.5s，避免卡在 SQL
- 进程外：`server/rss-watchdog.mjs`，盯父进程 RSS，≥3200MB `SIGKILL`
- 重启前 `parkWorkForRestart`：把本实例 running 退回 pending，避免任务标失败（事件循环还活着时才有用）

### 4.3 浏览器与子进程

- mail.com 验密：`mailbox-service.verifyMailcomLogin` 派 `scripts/worker-mailcom-verify.ts`，主进程不再开 Playwright
- 去掉 50s 验密 `Promise.race`（假失败 + 孤儿 Chrome）
- consent 墙只认 URL，不再扫首页 cookie 文案
- mail.com Chrome 槽位 1–2
- 页面验密并发 2
- worker stdout 512KB 封顶
- 启动时最多恢复 1 条换绑；可用 `SKIP_STARTUP_RECOVERY=1` 完全跳过

### 4.4 产品行为

- 导出 sub2json：缺 RT 时先取再导；另有导出卡住时，**已有 RT 的子集仍可导出**
- RT 并发读配置 `rtConcurrency`（1–20，默认 4），不再写死 2
- GPT 跳板空 → 直连代理池
- 10808 在 dispatcher 里强制 HTTP

### 现在可以怎么开

| 操作 | 并发 | 说明 |
|---|---|---|
| 测 AT / 刷 RT / 导出 sub2json | 配置值，默认 **4**（1–20） | 主进程不再起转发环，**不必改成每次 1 个** |
| 充值预检 | 充值并发，最多 3 | 短连接 |
| mail.com 验密 / 页面验密 | **2** | 子进程 Chrome |
| 邮箱整备 / Gmail 比特开窗 | **本轮关闭领取** | 不是限成 1，是整类先停 |
| 启动换绑恢复 | 跳过 | 防止一启动又把 CDP 接回 3100 |

导出 JSON 里每个账号的 `"concurrency": 1` 是给下游 sub2api 的字段，与这边一次跑几个号无关。

## 6. 还没拆干净（再卡多半从这里来）

架构上 `:3100` 仍是 HTTP + SSE + DB + 调度的神进程。下面这些若再进主进程，还会涨内存：

1. **Gmail 整备 / 换 2FA / 比特 CDP**（`google-secure.ts` `withGoogleBitSession`）仍可从 3100 调。应整段派 worker，与 mail.com 验密同一模式。
2. **换绑对账 / 启动恢复** 仍可能 `enqueueGmailRebind`。没开 `SKIP_STARTUP_RECOVERY` 时启动会捞 1 条。
3. **`probeMailProxy` / 比特开窗** 在 worker 里仍用 `wrapExitThroughJump`（允许）。不要把 `ALLOW_LOCAL_SOCKS_RELAY=1` 设回主进程。
4. **SSE 写给已断开的浏览器**（`CLOSE_WAIT`）会拖事件循环，不是 40GB 主因，但卡死时会一起出现。
5. **IMAP 拉全文 MIME** 曾在主进程读大信。已改为信封优先、OpenAI 类邮件 80KB 封顶；仍建议 IMAP 也进 worker。

未完成业务债（与 OOM 无关，避免丢上下文）：

- `beibe`（约 4080）日志里抽出的 TOTP 可能没写回库
- 库里 TOTP：多数 `last-extract == current`；ChatGPT MFA 与 Gmail 2FA 不是同一把密钥
- 持久化换绑事件表、force-email-login 策略未收口

# 只应看到 *:3100。若再出现 127.0.0.1:5xxxx LISTEN，就是转发环又进来了

卡死时不要等它自己恢复：HTTP 已经死了，`parkWorkForRestart` 也跑不了，直接 `kill -9` 监听 3100 的进程。

恢复整备之前，先把 Gmail/比特开窗迁出 3100，否则会回到本报告第 2.3 节。

## 8. 一句话

**:3100 只做 HTTP / SSE / 队列 / 写库。带流量的代理转发、Chrome、比特 CDP 全部进子进程。并发数字管的是任务数，管不住一条没关上的流。**
